# Current-State Architecture

ReconForge is a local-first Python modular monolith with a FastAPI v1 surface,
Typer CLI, server-rendered Studio, experimental React client, SQLite migrations,
and optional DuckDB analytical reads.

## Implemented boundaries

```text
reconforge/
  api/             FastAPI app, dependencies, auth and versioned routes
  auth/            local users, passwords, sessions and RBAC foundations
  audit/           append-only SQLite hash-chain events
  db/              SQLite connection, migrations, backup and export/restore
  engines/         Pandas and genuine DuckDB local execution adapters
  reconciliation/  stock-to-GL and work-order reconciliation
  platform/        local finance, inventory, bounded payables, close, controls, matching and evidence services
  workflow/        state-machine and transition persistence
  studio/          current local UI bridge and request guards
apps/web/          read-only experimental React/Vite showcase
control-packs/     declarative YAML rules, mappings, risk models and examples
tests/             unit, integration, API, security, migration and regression tests
```

## Important current limitations

- SQLite remains the default persistence backend for local API and Studio services. An explicit PostgreSQL server profile now provides API identity, RBAC, hashed sessions, principal propagation, bounded master-data collections including fiscal periods, a bounded Finance Core account/posted-entry/trial-balance API, audit-chain reads/verification, bounded close-control periods/tasks, and bounded evidence metadata/coverage backed by PostgreSQL, while remaining legacy domain routes stay on tenant-isolated SQLite; reconciliation, the rest of Finance Core, workflow, and other domain repositories are not yet PostgreSQL-backed.
- The PostgreSQL PPA API is deliberately server-profile-only. Local mode returns an explicit unavailable response rather than silently using SQLite. The route contract is tested with an authenticated synthetic principal; live evidence is limited to the underlying PostgreSQL persistence gate and does not establish hosted API availability.
- Optional database-per-tenant API routing is implemented with strict tenant-ID/path validation and per-tenant domain databases. The PostgreSQL server-auth profile requires this router until domain repositories migrate to PostgreSQL; hosted shared-schema deployment and full domain-service integration are not implemented.
- The transactional outbox uses formal SQLite migrations 13-14 and now has local claim leases, retry/backoff, publisher injection, replay, dead-letter bookkeeping, and a bounded local worker runtime. PostgreSQL migration `0007_postgres_outbox_delivery` adds tenant-scoped worker ownership, `FOR UPDATE SKIP LOCKED` claims, retry/dead-letter/replay transitions, and a fresh-connection `PostgresOutboxWorker`; external transport, publisher idempotency, tenant enumeration, and deployment scheduling remain explicit operational dependencies.
- Inventory planning, FIFO valuation, and valuation reversal mutations now append audit/outbox evidence inside their repository transactions; other legacy platform services still require migration.
- The AP slice stops at governed workflow and matching; invoice posting, statutory tax/withholding, payment execution, and ERP writeback are not implemented.
- The AR slice stops at governed invoicing, credit controls, receipts/allocations, exposure, and aging; statutory revenue/receivable posting, tax, credit notes, dunning, payment execution, and ERP writeback are not implemented.
- Financial columns outside account reconciliation, journals, intercompany, matching, AP, and the core reconciliation path are not uniformly minor-unit/Decimal storage.
- DuckDB now registers CSV inputs into DuckDB relations and runs shared reconciliation in-memory for small inputs; large local workloads are partitioned by normalized `work_order` keys and processed through bounded relation-native batches before merging deterministic results. Hosted execution still uses tenant-scoped PostgreSQL-cursor partitions and resumable output checkpoints; distributed queue scaling and hosted global relation-native assignment remain open.
- The React Studio is a read-only experimental client and does not constitute a complete ERP frontend.
- The central policy foundation now has a read-only `enterprise-policy-conflict-analysis-v1` artifact and CLI. It canonically analyzes tenant-bound grants for overlapping SoD permissions, service-account human permissions, unscoped privileged grants, and duplicate active grants without mutating authorization. Provider-backed policy administration, complete route/job/export/UI adoption, distributed invalidation, and deployed effectiveness remain open.
- PostgreSQL policy administration now has a read-only `PolicyAnalysisApplicationService`/`PostgresPolicyAnalysisRepository` boundary and `POST /api/v1/admin/access/policy-analysis`. The route requires human-only `security.policy.manage` plus an independent prior approval timestamp, loads active RBAC, persisted bounded role-permission scopes, exact optional amount bounds, and enabled service-account grants under tenant RLS, and reuses the same digest-bound analyzer. CI server-boundaries run `30808822315` verifies migration `0059_pg_policy_amt_bounds`, RLS, projection, and tamper/revocation behavior under a non-privileged role. Currency conversion, provider federation, distributed invalidation, and complete route/job/export/UI adoption remain open.
- Evidence registration now supports an explicit object-store injection path and CLI `evidence register --storage-backend s3`, including tenant-scoped keys and provider-verified checksums. PostgreSQL migration `0008_postgres_evidence_registry` adds tenant-scoped metadata, immutable artifact identity guards, links, requirements, coverage, and verification state; report writers, worker delivery, malware scanning, signed-download authorization, and restore/object replication workflows remain local or unintegrated.
- Alembic covers the PostgreSQL tenant/RLS foundation, bounded master-data schema, bounded ledger-control schema, identity schema, close-control schema, outbox delivery metadata, evidence registry, and reconciliation result persistence; the remaining Finance Core, workflow, and other domain schemas are not yet represented in the PostgreSQL migration chain.

## Trust boundary

The trusted boundary is the operator-controlled machine, local files, SQLite database,
and generated evidence directory. Local API requests are explicitly untrusted unless
they resolve to an authenticated local user; the optional server profile binds a
tenant-scoped PostgreSQL principal and applies its permission snapshot to legacy
tenant-local domain services. The application is not currently a public SaaS or
complete multi-tenant ERP service. Any hosted deployment still requires separate
domain persistence, identity lifecycle, storage, and operational controls.
