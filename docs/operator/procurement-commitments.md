# Approved purchase appropriations

This experimental PostgreSQL contract binds a **new native multiline purchase** to one approved native budget. It uses the existing budget, procurement, FIFO, supplier AP, financial posting and installment engines. Install the complete migration chain through `0127_pg_procurement_commitments`; integration supplies its final predecessor.

In **Budget control**, select the actual canonical workspace, organization and entity. Create the budget draft with its fiscal period, currency and positive exact minor-unit limit; submit it and have an independent human approve it. Configure the normal supplier, stock items, units, warehouses, FIFO policies, open fiscal period, journal, AP and cash accounts. Appropriation currency and period must equal the original purchase.

In **Partial procurement**, choose **Enterprise order with multiple lines** and **Reserve approved purchase appropriation**. Begin the purchase number with `BPC1-`, select the approved appropriation, fill its reservation reason, and enter every original merchandise quantity, unit price and receiving location. The initial limit is 128 lines. **Create purchase order** reserves the entire original merchandise value atomically with the native Draft PO. Rejected creation leaves no obligation or purchase behind. Submit the original order and have a different human approve it using the existing workflow.

Receive partial quantities normally: prepare each line, independently review, and have a third human post stock receiving and GL. Native source prices and exact unit precision remain authoritative. Match the received quantities to a multiline supplier invoice, independently approve it, prepare its AP accrual and have an independent reviewer validate it. The third poster uses **Post AP and consume appropriation**, which publishes native AP and consumes the same exact obligation together. The detached original **Post invoice accrual** route refuses BPC1 sources.

Reads require `budget_control.read` in addition to existing `payables.read`, `inventory.read`, and `finance_core.read`. Every mutation also requires current `budget_control.manage` and the existing procurement action permissions. Posting requires the native third-human AP posting permissions; release requires `payables.approve` and a human different from the original purchase preparer. Current persisted scope grants, amount policy and privileged-session assurance are checked on new commands and retries.

To close the unreceived remainder, open **Purchase appropriation**, refresh its current native budget version, enter a release date and the shared review reason, then select **Release remaining obligation** as an independent authorized human. Release is refused while any receiving/invoice draft is incomplete, or any received per-line quantity is not accrued. The entire remaining unreceived amount is released. The original native source, documents, evidence and command receipts remain retained; subsequent receiving or purchase progression is prohibited. Already accrued AP may still be settled with the existing independently reviewed installments after release.

For `10 EA × 1200` and `2.50 KG × 2000`, the original obligation is `17000` minor units. Receive and accrue `2 EA` and `2.50 KG`: native inventory and AP are `7400`, with `9600` still reserved. Independent release returns `9600`; an approved envelope of `20000` then has consumed `7400`, reserved `0` and available `12600`. Separate native installments of `2400` and `5000` settle AP; the independent expected receipt/AP/payment GL turnover is `22200` on each side. Quantities across different units are never added.

The displayed amounts are exact minor-unit strings. The displayed current budget version belongs to the whole native envelope; other purchases can advance it. A version conflict requires a fresh budget read and a new command. A transport error or lost response retains the exact command ID, original versions, payload and source. Use **Retry exact appropriation command**; editing or preparing another obligation remains locked until the outcome is confirmed. Retained historical acknowledgements never replace a newer terminal release already observed by Studio. The server rechecks current authority before returning a cached success.

Paid landed-cost bundles are currently refused on BPC1 sources. Their cash charge and capitalized receipt value require an explicit appropriation contract; selecting a merchandise budget does not fund freight or duties. This slice supports the original zero-tax functional-currency procurement contract and the original appropriation fiscal period. Supplier returns, debit notes, budget reinstatement, PR/RFQ/quotations and manufacturing are separate complete cycles.

For input failures, check the `BPC1-` prefix, matching approved budget period/currency, exact integer prices, per-line unit precision, required master references, canonical scope and nonempty reasons. For version or authority failures, refresh source and budget independently and verify the current role/scope grants and privileged session. For an unresolved response, retry the exact saved command. Diagnosis must preserve native events, audit, outbox, financial effects and command receipts.

The existing ceilings remain 128 lines, 1024 receipts and invoices per purchase under native document limits, and 1000 total Reserve/Consume/Release events per approved envelope. Terminal release does not recover document-number or immutable-history capacity. These ceilings are admissions, not measured throughput promises; a separate 1000-line journal fixture proves no 1000-line procurement capability.

Empty rollback may remove only empty BPC1 tables and restore the prior procurement verifier. A subsequent upgrade recreates those tables; restore the app table ACL confirmed before rollback through the deployment role bootstrap. Populated native appropriation history refuses downgrade. Use forward correction or a verified pre-upgrade backup restore. Include native budget envelopes/commands/events and both BPC1 tables in source-bound populated snapshots, then replay native budget, procurement and financial verification after restore.

Relevant verification commands are `.github/scripts/verify_commercial_collections.py tests/test_postgres_procurement_commitments.py tests/test_postgres_procurement_commitments_api.py` and, after integration registers its scenario, `.github/scripts/verify_erp_expansion_browser.py --scenario procurement-commitments --verify-native-restore`. Final evidence must name the exact clean source commit, actual case counts without skips, retained failures, native fingerprints, raw timings and restore result.
