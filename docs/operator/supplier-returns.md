# Original supplier return and debit

This experimental PostgreSQL workflow returns one complete unused original receipt and credits its exact matching accrued unpaid supplier invoice. In Studio open **Partial procurement**, select the approved multiline purchase and inspect its retained source. Select the whole posted receipt and its single-line accrued invoice in **Original receipt supplier debit**. Enter an `SR1-` number, an open corrective period, a date no earlier than the original receipt/AP effects, an existing expense account, and a reason. The selected line must have one complete receipt/invoice and no issued FIFO quantity, payment or outstanding draft.

The preparer creates native inverse drafts. A different human reviews; a third human posts. Confirm privileged access when the session requires it. Each step requires current native reverse/post permissions and persisted workspace, organization and legal-entity grants. Because evidence retains the original purchase header, amount authority covers the larger of the entire original purchase total and the correction's twice-capitalized-cost burden at original precision. Review the original merchandise credit, capitalized stock removed, paid-charge expense, complete financial burden and retained digest before proceeding. Native source references, inverse plan, original and corrective financial effects, actor events and evidence remain inspectable.

For ordinary original merchandise B and capitalized inventory C, posting removes C from original FIFO, credits supplier AP B and expenses C−B. The expense account matters only when original paid freight/duties exist. Those original paid charges stay paid; the workflow creates no cash refund. With an original 10 EA merchandise invoice of 12000 and capitalized FIFO value 12706, posting credits AP 12000, removes inventory 12706 and expenses 706. A separate original 2.50 KG line remains independently payable. Never add quantities of different units.

AP shows terminal **Credited**, the immutable native supplier credit link and zero outstanding value. Procurement retains original receipt/invoice quantities and received/accrued amounts; credited, paid and outstanding amounts conserve the original obligation. The initial return does not create replacement receiving capacity. Prepare replacement procurement as an independently governed new purchase when required.

Before posting, an independent permitted human can cancel a Prepared or Reviewed return. Cancellation clears its pending receipt/AP claims so ordinary settlement or a newly prepared return can proceed. It retains original inverse drafts, native financial drafts, review and command evidence. A posted return cannot be cancelled or silently edited.

If a response is lost or its acknowledgement cannot be verified, use **Retry the same supplier return command** in the same selected scope. The exact command ID, payload and expected digest are retained. Do not create a second correction to compensate for a missing response. Current permission and authority still apply on retry; a revoked grant cannot retrieve an earlier successful response. A confirmed terminal response remains visible when a follow-up list refresh fails. Refresh the source to reconcile other participants' newer state.

Input errors appear beside the form. A disabled prepare action requires a complete source selection, number, date, period, expense account and reason. A network error retains the command; a definite server rejection clears only that rejected command. Source conflict means the original receipt, AP, quantity, payment or current claim no longer satisfies this contract. Inspect original evidence and current status before a new attempt. Do not change SQL rows to repair an owner error.

The API uses `/api/v1/supplier-returns/plans` for preparation, `/plans/{id}` for exact inspection, `/orders/{order_id}` for the newest 25 retained owners and `/plans/{id}/review`, `/post` or `/cancel` for lifecycle commands. Mutations require cookie authentication, CSRF, selected canonical scope, current session assurance, a reason, command ID and expected plan digest where applicable. Monetary outputs are exact decimal integer strings; `canonical_plan_json` and `plan_digest` retain source evidence.

Limits: one complete unissued receipt and matching single-line unpaid zero-tax AP invoice; no paid/part-paid invoice return, partial return, tax/FX correction or BPC1 appropriation reinstatement. Existing purchase limits remain 128 lines and 1024 receipts/invoices. Capitalized cost is at most 4500000000000000000 minor units and complete correction burden at most 9000000000000000000. These are admission limits, not throughput acceptance.

Migration 0130 is additive. Empty downgrade restores previous native verifier bodies and removes empty owner state; restore deployment-role ACL after recreating tables. Any retained return owner, including a cancelled draft, refuses downgrade to protect original/inverse/evidence history. Use forward correction or an independently verified pre-upgrade backup. Populated restore acceptance must compare native financial/source/owner rows, functions, triggers, constraints, RLS and ACL fingerprints and repeat independent financial oracles.

The real HTTPS scenario `erp-supplier-returns.spec.ts` seeds only masters and three principals. Studio creates the mixed-unit purchase, pays landed charges, receives both source lines, accrues AP, independently reviews and cancels a first claim, then prepares and posts a fresh claim against the same whole EA receipt and unpaid invoice. Refill the replacement number, source selections, date, fiscal period, expense account and reason after refreshing the order. The cancelled reviewed native inverse retains its evidence with no published link. Studio pays the remaining KG invoice in two installments. The independent expected final state is 10 posting effects, balanced turnover 66414, stock 5295, cash change −6001, AP/clearing zero and charge expense 706. Count this runtime proof only when a clean source-bound report records successful wire and populated restore.
